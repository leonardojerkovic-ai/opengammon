# Rules notes

Findings about backgammon rules edge cases, checked against GNUbg (as an external process or
by reading its source for understanding), recorded here as they come up during Phase 1.

## GNUbg's `hint()` MAX_MOVES cap does not truncate on dense positions

`gnubg_harness.py` asks GNUbg for legal moves via `gnubg.hint(MAX_MOVES)`, capped at 5000. The
8 named edge-case tests only ever exercised this against sparse, synthetic positions (1-2
checkers on the board), so the cap was untested against dense, realistic positions where
branching is actually high.

Checked empirically (`dense_positions_are_not_truncated_by_max_moves_cap` in
`crates/og-core/src/gnubg_diff.rs`): 30 positions generated by random self-play from the
starting position (4, 8, and 15 turns in, all 30 checkers still on the board — the branchiest
phase), each compared against GNUbg's own result at MAX_MOVES=5000 versus MAX_MOVES=200000,
across all 21 rolls. Identical result sets in every case — no truncation observed at the
default cap. 5000 stands as the harness's cap.

Each of these calls (dense position, deep `hint()` evaluation) took ~200ms — noticeably slower
than the sparse-position calls used for the 8 named tests. This is the concrete cost that
motivates the persistent gnubg-cli process (CLAUDE.md §0): at ~200ms per spawn, a
million-position run at 21 rolls each is not viable with one process per call.
